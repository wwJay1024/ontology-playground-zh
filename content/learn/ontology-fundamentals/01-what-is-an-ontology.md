## 用图的方式思考

假设你要描述一家咖啡店。你会谈到各种**事物**——门店、商品、客户、订单——也会谈到它们之间的**联系**：客户*下单*，订单*包含*商品，门店*备有*商品。

**本体**正是对这件事的形式化描述：一个领域里有哪些类型的事物，它们彼此如何关联。它是数据的蓝图——不是数据本身，而是数据的*形状*。

## 实体、属性与关系

每一个本体都由三块积木搭成：

| 概念 | 含义 | 示例 |
|---------|--------------|---------|
| **实体类型** | 一类事物 | `Customer`、`Product`、`Store` |
| **属性** | 关于某个实体的一条事实 | `Customer.name`、`Product.price` |
| **关系** | 实体之间的联系 | `Customer → places → Order` |

属性带有**类型**——文本、数字、日期、布尔值——每个实体还至少需要一个**标识属性**（比如客户 ID），用来唯一区分每一个实例。

## 本体为什么重要

没有本体，数据只是一堆表和列。有了本体，系统就能理解「营收」指的是把 `Order.totalAmount` 按 `Store.city` 分组求和——因为本体告诉它这些概念之间怎么连接。

这正是**语义数据模型**的基础：你不必手写 SQL，只要用自然语言说清想要什么，系统就会借助本体生成正确的查询。

## 从概念到代码

本体通常用 **RDF/OWL** 表示——这是一套基于 XML 的标准，用来描述类、属性和关系。不过你不必手写 XML：[本体设计器](#/designer) 这类工具可以让你在界面上把本体搭出来，再导出符合规范的 RDF。

## 要点回顾

- 本体定义了一个领域里**有哪些类型的事物**，以及**它们如何关联**
- 它是模式，不是数据——描述形状，不描述内容
- 它让语义查询成为可能：用自然语言提问，拿到结构化答案
- 标准格式是 **RDF/OWL**，不过也可以用 JSON 表示

```quiz
Q: 下列哪一项不是本体的组成部分？
- 实体类型
- 属性
- SQL 查询 [correct]
- 关系
> 本体由实体类型、属性和关系构成。SQL 查询是取数据的手段，并不属于本体定义本身。
```

```quiz
Q: 标识属性的作用是什么？
- 保存实体的颜色
- 唯一区分实体类型下的每一个实例 [correct]
- 把两个实体连接起来
- 定义数据格式
> 标识属性（比如客户 ID）在同一个实体类型内部唯一标记每个实例，系统靠它才能正确计数、分组和连接。
```

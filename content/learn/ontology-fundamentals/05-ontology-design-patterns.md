## 命名要照顾人

设计时最重要的决定就是命名。实体类型和属性既给人看，也给机器读——名字清楚，自然语言查询就更准。

**推荐做法：**
- 实体类型用单数名词：`客户`、`商品`、`订单`
- 属性用小驼峰命名：`firstName`、`totalAmount`、`createdDate`
- 关系用动词短语：`placedBy`、`worksAt`、`contains`

**避免：**
- 内部表名：`tbl_cust_v2`、`DIM_PRODUCT`
- 各种缩写：`qty`、`amt`、`dt`——写全
- 泛泛的名字：`Item`、`Record`、`Thing`

## 一个实体，一个概念

每个实体类型只对应**一个业务概念**。如果你发现自己在往里塞不相干的属性，多半就该拆开了。

**反模式：** 一个 `Person` 实体同时带着 `salary`、`patientId`、`courseGrade`、`accountBalance`——这其实是四个概念（员工、患者、学生、客户）硬压进了一个实体。

**更好的做法：** 拆成几个独立的实体类型，需要时再把它们关联起来：一个 `Person` 可以连到一条 `Employee` 记录、一条 `Patient` 记录，等等。

## 慎重选择标识属性

标识属性决定了实例怎样被计数、分组和连接。好的标识属性满足三点：

- **唯一**——在所有实例中不重复
- **稳定**——不随时间变化
- **有意义**——最好是业务主键，而不是内部自增 ID

例如：书的 `isbn`、用户的 `email`、订单的 `orderId`。

尽量不要用复合标识（多个字段合起来当键）——多数本体工具只接受每个实体一个标识属性。

## 建关系，而不是外键

关系型数据库靠外键把表连起来。在本体里，用的是**带名字的关系**，语义直接写在名字里。

| 关系型做法 | 本体做法 |
|-----------|----------|
| `orders.customer_id → customers.id` | `订单` → `placedBy` → `客户` |
| `order_items.product_id → products.id` | `OrderItem` → `contains` → `商品` |

关系的**名称**很关键：它告诉查询引擎（也告诉人）这条连接是什么意思。「placedBy」比一个叫 `fk_cust_id` 的列清楚得多。

## 基数要设对

基数错了，聚合结果就错。问自己一句：「一个 A 的实例，能对应多少个 B 的实例？」

- 一个客户可以下**多个**订单 → 一对多
- 一个订单只在**一家**门店产生 → 多对一
- 一个学生可以选**多门**课，一门课也有**多个**学生 → 多对多

*医疗本体很适合用来琢磨基数：一位患者有多次预约，但每次预约只有一位接诊医生。一个诊断属于一位患者，却可能关联多张处方。*

## 避开这些常见错误

| 错误 | 问题 | 改法 |
|---------|---------|-----|
| **上帝实体** | 一个实体塞了 30 多个属性 | 拆成几个职责单一的实体 |
| **缺少标识属性** | 无法计数或分组 | 补一个唯一的标识属性 |
| **关系名含糊** | `relatedTo`、`hasLink` | 换成具体动词：`prescribes`、`enrolledIn` |
| **互相指向的一对一** | A → B 和 B → A 都是 1:1 | 多半是同一个实体——合并 |
| **过度建模** | 每张内部表都变成一个实体 | 建用户会查询的概念，而不是照搬数据库模式 |

## 什么时候该写描述

实体类型、属性、关系都可以带一段可选的**描述**。遇到下面这些情况就该写：

- 光看名字有歧义（`status` 可能指很多意思）
- 概念是行业专有的（`formulary`、`SKU`、`yield`）
- 你想引导自然语言查询的理解方向

## 要点回顾

- 命名照顾人：单数名词、小驼峰、动词短语
- 一个实体一个概念，负担过重的实体要拆开
- 选稳定、唯一、有意义的标识属性
- 用带名字的关系建模，而不是外键列
- 把基数设对，聚合才靠得住
- 名字有歧义的地方补上描述

```quiz
Q: 一个 Person 实体带着 salary、patientId、courseGrade、accountBalance 四个属性，应该采用哪种设计模式？
- 补一个标识属性
- 把所有属性合并进一个描述字段
- 拆成独立的实体类型（Employee、Patient、学生、客户），再建立关系 [correct]
- 只留一个属性，其余删掉
> 实体一旦堆积了互不相干的属性，就成了「上帝实体」。正确的做法是把每个概念拆成独立的实体类型，需要时再用关系连起来。
```

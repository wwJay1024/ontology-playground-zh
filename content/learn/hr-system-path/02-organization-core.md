## 搭建组织骨架

每个人力资源本体都从三个核心实体开始：

- **员工**——组织中的具体的人
- **部门**——工作得以组织的业务单元
- **岗位**——描述职责与层级的角色定义

这三个实体构成了招聘、汇报关系与人力规划所需的最小结构。

## 实体设计

### 员工

| 属性 | 类型 | 是否标识属性 |
|---|---|---|
| `employeeId` | string | ✓ |
| `name` | string | |
| `hireDate` | date | |
| `employmentStatus` | enum | |
| `jobLevel` | enum | |

`employeeId` 是稳定的业务标识。不要把邮箱这类会变的属性当作主键。

### 部门

有了部门预算，资源规划与成本中心分析可以在同一张图谱上完成。

### 岗位

| 属性 | 类型 | 是否标识属性 |
|---|---|---|
| `positionId` | string | ✓ |
| `title` | string | |

岗位把角色定义与当前任职的人分开。

## 为什么要这样拆分

如果把这几类概念塞进一个“员工档案”实体，以下场景就会失去灵活性：

- 历史任职变动
- 角色转换
- 招聘之前就已存在的空缺岗位

拆成独立实体，模型才干净、可扩展。

```quiz
Q: 为什么要把岗位建成独立实体，而不是只在员工实体上存角色字段？
- 因为本体工具要求至少有三个实体
- 因为岗位是可复用的角色定义，可以独立于具体员工存在 [correct]
- 为了减少关系数量
- 为了避开标识属性
> 岗位代表角色本身（职称、层级、薪酬带宽），员工代表具体的人。把两者分开，才能表达空缺岗位、岗位转换，也才能做更清晰的任职分析。
```

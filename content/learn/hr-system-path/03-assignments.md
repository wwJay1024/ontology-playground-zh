## 任职历史带来的难题

员工会随时间在部门或岗位之间流动，一个部门可以容纳多名员工，一个岗位在不同时期也可以由不同的人担任。

这不是简单的一对一结构。

## 用关联实体表达任职

创建**任职**实体，连接：

- `Employee` -> `Assignment`（一对多）
- `Assignment` -> `Department`（多对一）
- `Assignment` -> `Position`（多对一）

任职保存的是这段关系自身的上下文。

### 任职的属性

| 属性 | 类型 | 是否标识属性 |
|---|---|---|
| `assignmentId` | string | ✓ |
| `startDate` | date | |
| `endDate` | date | |
| `isPrimary` | boolean | |

有了 `startDate` 和 `endDate`，就能回答这类历史问题：

- “第二季度谁在财务部？”
- “今年哪些员工换过部门？”

## 设计模式的实际应用

这在很多领域都是同一个通用模式：

- 学生与课程，通过选课关联
- 客户与商品，通过订单行关联
- 员工、部门与岗位，通过任职关联

当关系本身需要携带属性时，就用关联实体。

```quiz
Q: 任职应当独立成实体，主要原因是什么？
- 这样图谱里的图标更好看
- 它能承载关系自身的属性，比如 startDate 和 endDate [correct]
- 这样就不需要标识属性了
- 它能避免多对一关系
> 任职记录的是任职关系在时间上的上下文。这些属性属于关系本身，而不属于员工、部门或岗位中的任何一方。
```

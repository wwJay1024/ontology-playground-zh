## 订单发生在哪里

到目前为止，我们知道*谁*买了*什么*，但不知道*在哪里*。Fourth Coffee 在多座城市都有门店，每张订单都在某家具体门店处理。

加入 **门店** 实体后，就能回答与位置有关的问题：
- 「哪家门店的订单最多？」
- 「各城市的平均客单价是多少？」
- 「按订单量看，哪些门店需要增加人手？」

## 门店 实体

| 属性 | 类型 | 是否标识属性？ |
|---|---|---|
| `storeId` | 字符串 | ✓ |
| `name` | 字符串 | |
| `city` | 字符串 | |
| `state` | 字符串 | |
| `openDate` | 日期 | |
| `capacity` | 整数 | |

`capacity`（座位数）是**整数**类型，排班和运营规划都会用到。`city` 与 `state` 提供了地理信息，又不必引入完整地址层级那样的复杂度。

## 新关系

- **processedAt**——`订单` → `门店`（多对一）
  每张订单只在一家门店处理，而一家门店会处理很多订单。

> **设计说明：**这是一条多对一关系。多张订单对应一家门店。「属于」「发生于」这类关系的基数大多如此。

## 小结

- **多对一关系**用来表达「属于」「位于」这类模式
- **整数属性**适合可数的量（容量、楼层、座位数）
- 增加一个实体，就打开了一整类与位置有关的查询
- `diff` 视图准确显示改了什么，本体演进因此容易追溯

```quiz
Q: 订单 与 门店 之间的 "processedAt" 关系应该是什么基数？
- 一对一——每家门店恰好有一张订单
- 一对多——每张订单在多座门店处理
- 多对一——多张订单在同一家门店处理 [correct]
- 多对多——订单可以同时在多座门店处理
> 每张订单只在某一个门店处理，而一家门店一天里会处理很多订单。站在 订单 一侧看，就是多对一。
```
